# 0011 — OpenClaw owns the channel, the gate owns the room

**Status:** Accepted 2026-08-12 — config in [`config/openclaw.example.json5`](../../config/openclaw.example.json5), integration mechanism is [Q6](../OPEN-QUESTIONS.md)
**Amends:** [0004](0004-signal-control-channel.md), [0007](0007-principals-on-the-control-channel.md), [0008](0008-authority-is-a-conversation-sender-pair.md), [0009](0009-agents-are-containers-that-ask-by-name.md), [0010](0010-profiles-are-pre-bound-grant-bundles.md)

## Context

`src/gate/signal.py` was written against a bare signal-cli daemon, on the assumption
that everything between the wire and an agent had to be built. A review of the
OpenClaw documentation on 2026-08-12 found that most of it already exists as
configuration, and that two things we had marked as work — approvals and per-agent
credential isolation — exist in a form at least as strong as the one designed here.

The relevant findings, each checked against a documentation page rather than
inferred:

- **The conversation and sender allowlists are config.** `channels.signal.dmPolicy`
  with `allowFrom`, `channels.signal.groupPolicy` with `groupAllowFrom`, keyed as
  `uuid:<aci>` — which matches what actually arrives on the wire (2026-08-11:
  `sourceNumber` is null on real traffic).
- **Per-(conversation, sender) grants are config.** `channels.signal.groups["<id>"]`
  carries `tools` and `toolsBySender`, resolved group-`toolsBySender` → group-`tools`
  → default-`toolsBySender` → default-`tools`, deny wins. ADR 0008's pair is
  expressible.
- **Confirmations are config, and better than ours.** Signal renders approval
  prompts as 👍/👎 reactions and `ask_user` prompts with 1–4 options as 1️⃣–4️⃣.
  Approvers come from `channels.signal.allowFrom` / `defaultTo`, approvals carry an
  id, and they expire (exec 30 min; plugin `timeoutMs` 120 s default, 600 s cap;
  `ask_user` `timeoutSeconds` 900 default). `approvals.plugin` extends this to
  arbitrary tool calls.
- **Per-agent isolation is config.** Sandbox scope defaults to `"agent"`, one
  container per agent id, with `agents.entries.*.sandbox.*` overrides. Auth lives per
  agent at `~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite`, with the
  warning "Never reuse `agentDir` across agents."

Hermes Agent was evaluated as the alternative and rejected on one project-specific
fact: its Signal allowlist is `SIGNAL_ALLOWED_USERS`, keyed on E.164 phone numbers.
We verified on hardware that Signal does not share numbers by default, so a
number-keyed allowlist matches nothing. Its authority model is also Admin/Regular
tiers over slash commands, with no group-scoped tool policy — the family group, which
is the centre of this design, is where it is thinnest.

## Decision

**OpenClaw owns the Signal channel, the agent runtime, the approval flow and the
credential mounting. The gate stops being a forwarder and becomes a guard on the
things OpenClaw does not model.**

### What moves to config

ADR 0004's control channel, ADR 0007's principals and ADR 0008's pair-scoped grants
are now expressed in `~/.openclaw/openclaw.json` rather than in `decide()`. The
[example config](../../config/openclaw.example.json5) is the normative statement;
what matters here is that four of its settings are load-bearing and none of them is
the default:

| Setting | Default | Ours | Why |
| --- | --- | --- | --- |
| `channels.signal.dmPolicy` | `"pairing"` | `"allowlist"` | Pairing lets an unknown sender request approval into the system. The posture in `load_config` is that an empty table refuses to start. |
| `session.dmScope` | `"main"` | `"per-channel-peer"` | `main` collapses every DM on every channel into one session. That is the thing ADR 0010 refuses: an agent session may not span conversations. |
| `agents.*.sandbox.mode` | `"off"` | `"all"` | Without it there is no container, and ADR 0010's enforcement is the container. |
| `channels.signal.configWrites` | `true` | `false` | ADR 0010: there is no message that grants a capability. A channel that can write config is that message. |

Three of the four defaults are wrong for this threat model in the same direction —
toward availability. That is not a criticism of OpenClaw, which is built for a
different median user; it is the reason the config file is checked into this repo
with an explanation per line rather than generated by a wizard.

### The one hole in credential isolation, and how it is closed

Per-agent auth stores have **read-through inheritance**: "When an agent has no local
profile, it resolves profiles from the default/main agent store at runtime." There is
no documented way to disable it, which means an agent's credential set is its own
plus whatever the default agent holds.

ADR 0010's claim is that a tool outside the bundle is absent rather than refused.
That claim survives, but it now rests on a structural rule instead of a config key:

**The default agent holds no credentials.** It is a bare responder with an empty
tool list, and every agent that can do anything is a non-default entry with its own
auth store. An agent cannot inherit what does not exist upstream. This is an
invariant `deploy/render-agents.py` must assert, not a thing to remember.

**Verified 2026-08-12, and it is worse than read-through.** A canary key placed only in
`main` was retrieved and sent upstream by `family`, which has no store file at all —
the provider returned 401, which is proof the key was found rather than missing. And
with any file-reading tool present, the agent reads arbitrary absolute paths as the
gateway uid, which owns *every* agent's auth store (mode 0600, same uid). So without a
container there is no credential boundary between agents at all — not merely a leaky
one. The tool list is what stands in for the container today, which is why the backend
now grants no native tools whatsoever. **Until `sandbox.mode` is real, "credentials are
per agent" is a statement about tidiness, not containment.**

Two mechanics that make this harder to hold than it looks: `--disallowedTools` does not
override `--tools` (the allowlist wins, so a capability must be removed from the
allowlist rather than added to the deny list), and **tool policy binds at session
creation** — tightening it leaves existing sessions on the old capability set until
their session store is cleared.

### What the gate keeps

Four responsibilities, none of which OpenClaw or Hermes models:

1. **Pinned group membership, and drift that refuses rather than degrades.** Neither
   framework verifies a member set; both allowlist a group id. This is not made
   redundant by `groupAllowFrom`, because it is an **egress** control, not an ingress
   one: a newly added member cannot command the agent, and reads every reply it puts
   in the room. `_members_of` and `_drifted` stay, and the `listGroups` poll stays.
2. **The outbound destination allowlist.** The built-in `message` tool takes a
   model-chosen target in a `channel:<id>` / `user:<id>` / `sms:<number>` grammar. The
   only lever in config is denying the tool outright. ADR 0009's "the agent writes a
   label, the gate resolves it, and the addressable set *is* the conversation table"
   has no equivalent — the agent would handle identifiers, which is the thing that
   design exists to prevent.
3. **Sender-granular agent routing.** `bindings[].match` selects on `channel`,
   `accountId`, `peer`, `guildId`, `teamId`, `roles` — per conversation, never per
   sender. The `owner-family` case from `config/example.config.toml` (same room, own
   session, wider profile) is not expressible as a binding. `toolsBySender` narrows
   that sender's *tools* but leaves them in the shared session, which is ADR 0010
   rule 2 inverted.
4. **Refusing to start on ambiguous config.** The six refusals in `load_config` have
   no counterpart; JSON5 with hot reload will accept a dangling profile name and a
   duplicate label without comment. `--check` printing the resolved matrix is the
   artefact for "what can this thing actually do", and it stays.

5. **Which senders may command in *which* room.** `channels.signal.groupAllowFrom` is
   channel-wide, and Signal's per-group config carries only `requireMention`, `tools`
   and `toolsBySender` — there is no per-group sender allowlist. So a sender admitted
   to groups is admitted to *every* allowlisted group. With one group that costs
   nothing; with a `family` room and a `confirmations` room it is wrong, and it is
   exactly the case ADR 0008 exists for. (Signal-specific thinness, not an OpenClaw
   limit — Telegram, Discord and Google Chat get per-room `allowFrom`.)

Everything else in `src/gate/signal.py` — the socket loop, backoff, envelope
filtering, the `decide()` allowlists, the ack path, the sent log — is duplicated work
and comes out.

### What becomes of a profile

ADR 0010's profile is a named bundle of tool instances bound to a pair before any
agent exists, with the container as the enforcement. Almost all of that survives, in
three pieces rather than one:

| ADR 0010 | OpenClaw |
| --- | --- |
| The pair's tool set | `agents.list[].tools` (per conversation, since a binding maps one conversation to one agent). **Not** narrowed by `toolsBySender` — see below |
| `alsoAllow` on top of a base | `tools.profile` (`minimal`/`coding`/`messaging`/`full`) plus `alsoAllow`; deny still wins at every level |
| The container is the enforcement | Per-agent auth store plus sandbox `scope: "agent"` — one container, one credential set, per agent |
| `send_to` | **No equivalent.** The proxy owns it (Q6 option E) |
| `[[agent.profiles]]` as a *named, reusable* bundle | **No equivalent** — `tools.profile` is a fixed built-in list, not user-definable, so a shared family bundle has to be repeated per agent |

**`toolsBySender` does not survive contact with a CLI backend** (verified on hardware
2026-08-12 by instrumenting the matcher; full trace in
[Q6](../OPEN-QUESTIONS.md)). It resolves correctly on the dispatch path, but a
CLI-backed agent is served over the MCP loopback, and the loopback context is rebuilt
from HTTP headers that carry no sender — `resolveGatewayScopedTools` passes only
`{config, sessionKey, messageProvider, accountId}` to `resolveGroupToolPolicy`, and no
`x-openclaw-sender*` header exists in the distribution. Sender identity collapses to a
single `senderIsOwner` boolean gating a fixed built-in list. This is not Signal-specific
and not fixable by config.

**Decision (2026-08-12): everyone in a room shares one tool set, until a stable
release carries the fix.** Upstream fixed this — `resolveGatewayScopedTools` now takes
`channelContext.sender` and feeds `resolveRequesterToolPolicies`, resolving sender once
at trusted ingress — but only in the beta channel (`v2026.7.2-beta.7` onward); npm
`latest` is still `2026.7.1-2`. Taking the beta was tried on hardware and rolled back,
because it **removes `agents.defaults.cliBackends`**, the only surface for passing
`--tools` / `--disallowedTools` to the Claude CLI. The CLI's native `Bash` is not
governed by OpenClaw tool policy, so on the beta the agent ran a shell as uid 991
despite `tools.deny: [exec, process, terminal, code_execution]`. A proven containment
floor outranks a capability ADR 0010 rule 2 never depended on. Tracked in NVB-21.

The claim above is therefore restated in the form ADR 0010 rule 2 already required:
**per-agent tool policy is enforced, per-sender-within-one-agent is not.**
`resolveEffectiveToolPolicy` keys on `sessionKey`, which the loopback does carry, so an
agent's own tool list holds. Varying capability per speaker inside one container was
always the runtime string check ADR 0010 deletes, so nothing that was load-bearing is
lost — but the mixed room (owner wider, everyone else narrower, same room) now costs
two agents and a proxy that routes senders to them, and is a live design question rather
than a config line.

The last row of the table is the one real ergonomic loss, and it is what justifies keeping
`config.toml` as the authoring surface: profiles stay named there, and the generator
expands them into per-agent tool lists in `openclaw.json`. The abstraction lives in
our config; the repetition lives in a generated file nobody edits.

### The registry changes job, and keeps its rules

`src/agent/registry.py` stops being a map from tool name to a systemd `LoadCredential=`
id and becomes a map from **our** grant vocabulary to **OpenClaw's** — tool ids, tool
groups (`group:fs`), and MCP server names. Its three rules are unchanged, because none
of them was about systemd: the verb stays the narrow one, a row is per account rather
than per capability class, and the credential is still the grant — it just lives in a
per-agent auth store or that agent's `sandbox.docker.env` instead of a mounted file.

It stays a closed dict, and it stays load-bearing for one reason the generator makes
sharper: **OpenClaw accepts a typo'd tool name in an allow or deny list without
complaint.** A misspelling in a deny list is a tool that is silently still granted.
The registry is what turns that into a refusal to start, which is the same argument
that put it there originally (ADR 0010) and the same argument for the other five
`load_config` refusals.

### What is deliberately given up

Approvals move in-process. OpenClaw's approval gate lives inside the agent runtime,
so it is code being correct rather than a credential being absent. Hermes' security
documentation states the general case plainly — *"Nothing inside the agent process
constitutes containment — not the approval gate, not output redaction, not any
pattern scanner, not any tool allowlist"* — and it is true of OpenClaw as well.

We accept it because the alternative is worse in practice: a reaction bound to a
specific delivered message is a stronger link between a YES and the action it
authorises than ADR 0008's quoted reply, and the registry that would have made ours
comparable (NVB-16) is unwritten. The mitigation is not a second approval gate; it is
that the credential behind an approved action was mounted into one container, so an
approval that is talked past still cannot reach a tool that container does not have.

## Consequences

**Accepted:**

- A large dependency, in TypeScript, on the trust path. The mitigation is that it is
  not on the *credential* path: agents are containers with their own auth stores, and
  the default agent is empty.
- Two config files with an overlap that must not drift — `config.toml` for the gate's
  conversation table, `openclaw.json` for the channel's allowlists. Whichever
  integration Q6 picks, one must be generated from the other; hand-maintaining both
  is the failure where the gate refuses a room OpenClaw still answers.
- MCP tools do not automatically get the approval gate — plugin approvals cover MCP
  only when Codex marks `_meta.codex_approval_kind`. Since the plan is to extend by
  MCP as trust grows, each MCP addition needs its approval story checked rather than
  assumed.
- **No cap on model spend, whichever credential backs it.** Nothing in OpenClaw's
  config caps per-conversation or per-agent model spend — `gateway.auth.rateLimit`
  covers pre-auth failures and control-plane RPCs only, and there is no equivalent of
  Managed Agents' per-session budget. An injection that induces a loop is a bill, or a
  burned subscription quota, as well as a security event. Billing and quota alerts are
  the mitigation until something better exists.

  Q4's hard constraint turns out to be narrower than it read. It rules out *pasting a
  subscription OAuth token into* a third-party tool; it does not rule out OpenClaw
  driving the locally installed Claude CLI, which authenticates natively as itself.
  OpenClaw supports that as a first-class provider
  (`openclaw models auth login --provider anthropic --method cli`), and `claude -p`
  usage draws on the signed-in Pro/Max allowance. The residual risk is not technical:
  a family group means people other than the account holder cause requests against
  that account's limits, which is the edge of Anthropic's "not on behalf of their
  users" line, and OpenClaw's own guidance is to use an API key for shared production
  automation. The owner decides which side of that line a household assistant sits on;
  the config supports either, and switching is one auth command.

**Gained:**

- Roughly 1,000 lines deleted, and the deleted parts are the ones that had to be
  verified against hardware envelope by envelope.
- Reaction-based approvals on Signal, which is NVB-16 substantially pre-built.
- A tool ecosystem the registry can grow into, instead of a closed dict that has to
  be extended by hand for every capability.
